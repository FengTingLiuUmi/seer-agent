# 因子关文档 `strategies[].why` 清洗规范

目标：给 `kb/docs/<因子名>/<难度>.json` 里**每一关的每一个 strategy** 补写 `why`，
说明「为什么这关要用这套打法」。产出要能被 AI 直接读懂并照着选阵容。

## 唯一允许改动的字段

- 只改 `stages[i].strategies[j].why`（字符串）。
- **不许动**：`doc_id / factor / difficulty / source_urls / stages[i].stage / apex / boss_* / traits / mech / pets / stages[i].why / strategies[j].text / source / plan / pets`。
- 原本非空的 `why` 如果已经符合风格，可以保留；不符合则重写。
- 同一个 stage 里多个 strategy 若机制相同，允许写**同一段** why（但不要互相复制粘贴成完全无关的内容）。

风格要点：

1. **短句，用空格断句**，不要长难句、不要书面腔、不要 markdown、不要分点符号。
2. **先给依据再给结论**：倍率 → 谁扛/谁打 → 关键技能或魂印 → 为什么这能过。
3. **必须带可核对的数字**：属性倍率（`1.125倍/1.5倍/2.75倍/4倍`）、Boss 血量（`15000`）、固伤（`500固伤`）、减伤（`减伤33.3%`）、技能威力（`150低体翻倍`）、PP/先制。
4. **点出这关的致命机制**，用「」引原文：如「免疫威力>100」「受到攻击消除我方能力提升状态」「每回合随机吸取我方3项属性+1并附加给自身」「单精灵挑战」。
5. **说清为什么不用别的路**：`不能强化` / `所以干脆不叠攻` / `有其他别用这个` / `ai尽量别用`。
6. 长度：一句到三句，**40–160 字**为宜；不要每关都写同样长，简单关可以很短。
7. 结尾不要句号（真人多数不加）；分句之间可用空格或`，`。

## 事实必须来自本体，不许编

> **本体已于 2026-11-25 补齐**：文档被点名的 546 只精灵里「有本体节点但 0 技能」已是 **0 只**。
> 因此**不需要**再跑 `onto_fill.py`（并发写同一文件会打架）。

- **先用现成上下文工具**（推荐，省掉几十次查询）：
  ```
  python seer-factor-kb/ontology/why_ctx.py <因子名> 地狱 > tmp/ctx.txt
  ```
  它会逐关打印：boss 属性/血量/`traits`、每个 strategy 的参战精灵（属性组合 + 自身属性打 boss 的倍率）、
  前 5 个技能（威力/先制/类别/必中/PP/效果全文）。多属性组合倍率反直觉，**以这个工具的实算结果为准**。
- 属性倍率也可单独算：`python -c "import sys;sys.path.insert(0,'seer-factor-kb/ontology');import type_multiplier as TM;print(TM.by_names(['自然','冰'],['飞行','电']))"`
  （注意 `type_multiplier.py` 直接跑 CLI 只做自测，不接收 argv）。
- 技能威力/先制/低体翻倍/必中/连击/PP：用 MCP 工具 `skill`（`pet` 或 `name`）查；本体没有就报告缺什么，**不要编数值**。
- Boss 血量/固伤/减伤/机制：直接取该 stage 的 `traits` / `boss_hp`（这是 SSOT）。
- 魂印效果：用 MCP 工具 `soulmark` 查。
- **`免疫威力` 方向要看原文**：`免疫威力<100`（只能用≥100）与 `免疫威力>100`（只能用≤100）完全相反，`mech` 里的 `immunePower` 不带方向，必须回读 `traits`。
- 无法核实的推断（如「X 回合能打死」），要么删掉，要么明确写 `未验证`。**不许把推测写成肯定句。**
- **不要**在 why 正文里写「未核实 / 本体未收录」这类话（AI 读起来是噪音）。查不到就换个能查到的技能名，
  或者干脆不写那个数字。
